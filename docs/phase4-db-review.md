# Phase 4 DB 변경 검토서 — 적용 전 승인 필요

**2026-10-28 적용 상태 갱신:** 사용자가 검토 후 신규 SQL 적용 완료를 알렸다. 이후 에이전트의 실제 공개 뷰/테이블 조회와 익명 save_review 권한 거부(42501) 검사가 통과했다. 사용자도 리뷰·즐겨찾기·마이페이지 직접 검사가 모두 정상이라고 확인했다. 아래는 적용 전 검토/절차 이력이며, 이미 적용한 파일을 다시 실행하지 않는다. 에이전트는 원격 SQL을 직접 실행하지 않았다.

대상: `supabase/migrations/202610280002_reviews_favorites.sql`. 초기 migration/seed를 다시 실행하지 않는다. 에이전트는 아직 원격 SQL을 실행하지 않았다.

## 변경과 위험

- 기존 7개 테이블, 데이터, RLS, 집계 view를 삭제하거나 초기화하지 않는다.
- reviews INSERT(id) 열 권한을 authenticated에 추가한다. 본인 user_id INSERT RLS와 identity 변경 금지 trigger는 그대로다. 사용자가 UUID를 지정해 같은 요청의 중복 등록을 방지한다.
- `save_review` SECURITY INVOKER RPC를 authenticated만 실행할 수 있다. 검증된 auth.uid(), 본인 소유권, 실제 태그 존재, 1~5점·본문1~5000자·최대10태그를 검사하고 리뷰/태그를 원자 저장한다. 새 UUID를 사용하면 같은 사람이 같은 식당에 여러 리뷰를 작성할 수 있다.
- `review_author_names`는 공개 리뷰의 `review_id`와 작성자 `display_name` **두 열만** 공개하는 owner 권한 view다. profiles 자체 RLS는 유지되지만 리뷰에 사용된 닉네임은 의도적으로 공개된다. 이메일/아바타/전체 프로필 조회는 열지 않는다. 공개 리뷰 정책이 바뀌면 이 view도 재검토해야 한다.
- 태그를 새로 만들지 않는다. 현재 실제 review_tags0건이므로 태그 없는 작성이 가능하고 UI에서 안내한다.

## 검증

신규 로컬 PGlite PostgreSQL 검사에서 원자성·후반태그실패 전체rollback·RLS A/B·중복UUID·반복리뷰·최신삭제평점복귀·태그cascade·즐겨찾기중복/격리·최소공개view가 통과했다. 직접RPC의 탭/개행만 있는 본문 허용 결함을 독립리뷰에서 발견해 실패테스트 후 수정했다. 이 결과는 원격 Supabase 쓰기 통합 검사와 구분한다.

## 적용 순서(사용자 승인 후)

1. Supabase 프로젝트가 이 앱과 같은 프로젝트인지 확인한다. SQL Editor에서 migration 파일 전체를 읽고 실행한다(표준 postgres migration 소유자). 권한이 낮은 anon/authenticated 계정으로 migration을 적용하지 않는다.
2. 전체가 begin/commit이므로 일부 객체가 이미 존재하거나 권한이 맞지 않으면 실패·rollback한다. 오류를 무시하고 부분 실행하거나 기존 사용자 데이터를 삭제하지 않는다. 이미 적용했다면 다시 적용하지 않는다.
3. 홈/상세에서 DB 준비 안내가 사라졌는지 확인한다. PostgREST schema cache 갱신에 잠시 시간이 걸릴 수 있다.
4. 실제 로그인 계정으로 본인 리뷰·즐겨찾기 CRUD/평점 검사를 진행하고, 다른 테스트 계정으로 타인 변경 거부를 확인한다. 기존 실제 리뷰를 지우는 테스트는 하지 않는다. 테스트에서 직접 만든 리뷰/즐겨찾기만 본인 계정으로 정리한다.

에이전트에 SQL 적용 결과만 알려주고 비밀번호·세션·키를 채팅에 공유하지 않는다. 에이전트는 원격 SQL 실행용 관리 도구가 없어 사용자가 직접 적용한다. 적용 전에도 즐겨찾기는 기존 테이블/RLS로 동작하도록 구현하며 리뷰 쓰기는 신규 DB 준비 상태를 안내한다.
